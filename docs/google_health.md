

# **PRD: Модуль фоновой синхронизации данных веса и состава тела из Health Connect**

**Статус:** Draft  
**Платформа:** Android (minSdk 26 / targetSdk 34+)  
**Интеграция:** Android Health Connect SDK (androidx.health.connect:connect-client)

## **1\. Контекст и цель (Overview & Objective)**

Умные весы (например, Tefal Goodvibes) сохраняют данные взвешиваний в локальное хранилище Android Health Connect. Цель фичи — разработать надежный фоновый модуль внутри существующего Android-приложения, который будет периодически опрашивать Health Connect, извлекать новые записи о весе и сопутствующих метриках состава тела, агрегировать их в единый слепок (DTO) и передавать в уже существующий модуль синхронизации с Garmin.

## **2\. Границы проекта (Scope)**

### **Входит в рамки (In Scope):**

* Запрос и управление разрешениями Health Connect (чтение метрик \+ доступ в фоновом режиме).  
* Первичная (историческая) выгрузка данных и инкрементальная синхронизация через механизм ChangesToken.  
* Склейка (корреляция) разрозненных записей Health Connect (вес, процент жира, мышечная масса и т.д.), сделанных в рамках одного взвешивания, в единую сущность.  
* Фоновый планировщик (WorkManager) и принудительный триггер при запуске приложения (Foreground sync).  
* Локальное хранение состояния синхронизации (токены, хэши/ID обработанных записей для идемпотентности).

### **За рамками (Out of Scope):**

* Логика авторизации и прямой отправки данных в Garmin Connect API (используется готовый интерфейс в приложении).  
* Прямое BLE-взаимодействие с весами.  
* Запись (Write) каких-либо данных обратно в Health Connect.

## **3\. Модель данных и маппинг (Data Mapping)**

В Health Connect каждая метрика сохраняется как отдельная независимая запись (Record). Чтобы сформировать полноценный пакет данных для Garmin (аналог структуры FitBodymass), модуль должен запрашивать следующие типы данных и группировать их по временному окну.

| Метрика (для Garmin) | Класс в Health Connect | Поле / Единица измерения | Обязательность |
| :---- | :---- | :---- | :---- |
| **Timestamp** | Все классы ниже | time: Instant | Обязательно |
| **Вес (Weight)** | WeightRecord | weight.inKilograms (Double) | **Обязательно (Якорь)** |
| **Процент жира** | BodyFatRecord | percentage.value (Double, 0–100%) | Опционально |
| **Костная масса** | BoneMassRecord | mass.inKilograms (Double) | Опционально |
| **Безжировая масса** | LeanBodyMassRecord | mass.inKilograms (Double) | Опционально |
| **Вода в организме** | BodyWaterMassRecord | mass.inKilograms (Double)\* | Опционально |
| **Базальный метаболизм** | BasalMetabolicRateRecord | basalMetabolicRate.inKilocaloriesPerDay | Опционально |

*\*Примечание по воде и мышцам: если клиент Garmin ожидает процент воды в организме, модуль должен высчитывать его по формуле (BodyWaterMass / Weight) \* 100\. Мышечная масса при необходимости берется из LeanBodyMassRecord.*

## **4\. Функциональные требования (Functional Requirements)**

### **FR-1: Управление разрешениями и доступностью SDK**

> 1. Приложение должно проверять статус Health Connect через HealthConnectClient.getSdkStatus(). Если сервис не установлен или требует обновления — отображать в UI плашку с предложением перейти в Google Play.  
> 2. Запрашивать у пользователя следующие разрешения:  
   * READ\_WEIGHT, READ\_BODY\_FAT, READ\_BONE\_MASS, READ\_LEAN\_BODY\_MASS, READ\_BODY\_WATER\_MASS, READ\_BASAL\_METABOLIC\_RATE.  
   * Разрешение на фоновую работу: android.permission.health.READ\_HEALTH\_DATA\_IN\_BACKGROUND.  
> 3. Если пользователь выдал права на чтение метрик, но отклонил фоновый доступ — синхронизация работает только при открытии приложения (в onResume главного экрана).

### **FR-2: Механизм получения изменений (Sync Engine)**

> 1. **Инициализация (First Run):** При первом запуске после получения прав запрашивается история за последние $N$ дней (например, 7 дней) через readRecords(ReadRecordsRequest) для всех целевых типов, чтобы не пропустить сегодняшнее взвешивание, сделанное до настройки. После этого запрашивается стартовый ChangesToken.  
> 2. **Инкрементальное чтение:** При каждом цикле синхронизации вызывается getChanges(token).  
> 3. **Обработка пагинации:** Если ChangesResponse.hasMore \== true, цикл вычитывает все страницы до конца, прежде чем приступить к агрегации.  
> 4. **Протухание токена (Token Expiration):** Токены Health Connect живут 30 дней. Если getChanges возвращает changesTokenExpired \== true, модуль автоматически делает fallback: запрашивает данные через readRecords с момента lastSyncTimestamp до Instant.now(), после чего генерирует и сохраняет новый токен.

### **FR-3: Алгоритм агрегации метрик (Time-Window Correlation)**

Поскольку приложение весов (Tefal / Google Fit) записывает вес и состав тела отдельными транзакциями с разницей в миллисекунды, модуль должен:

> 1. Найти все новые UpsertionChange, содержащие WeightRecord. Каждая запись веса считается «якорем» измерения.  
> 2. Для каждого WeightRecord (с временем ${T}_{weight}$) найти в пуле полученных изменений (или дозапросить через readRecords в диапазоне $[{T}_{weight}-60сек;{T}_{weight}+60сек]$) сопутствующие записи (BodyFatRecord, BoneMassRecord и т.д.) от того же источника (metadata.dataOrigin.packageName).  
> 3. Собрать единый объект BodyCompositionDto и передать его в интерфейс отправки Garmin.

### **FR-4: Фильтрация источников (Data Origin Filter)**

> 1. Предусмотреть в конфигурации (или настройках UI) белый список пакетов-источников (packageName), например: пакет приложения Tefal Goodvibes или Google Fit.  
> 2. По умолчанию принимать данные от всех источников, кроме самого нашего приложения (во избежание циклических петель, если когда-либо появится запись).

### **FR-5: Фоновый планировщик и триггеры**

> 1. **Background Trigger:** Использовать WorkManager (PeriodicWorkRequest) с интервалом 1–4 часа. Ограничения (Constraints): NetworkType.CONNECTED (так как после чтения данные сразу уходят по API в Garmin).  
> 2. **Foreground Trigger:** Запускать внеочередную проверку (OneTimeWorkRequest или корутину) при переводе приложения из фона на передний план (с троттлингом не чаще 1 раза в 5 минут).  
> 3. **Ручной триггер:** Кнопка «Синхронизировать сейчас» в UI приложения для отладки и мгновенной прокачки данных после взвешивания.

## **5\. Нефункциональные требования и Edge Cases**

### **NFR-1: Идемпотентность и дедупликация**

* Health Connect может вернуть одну и ту же запись повторно при сбое токена или обновлении метаданных.  
* Модуль обязан вести локальную таблицу в Room (или список в DataStore) с recordId (metadata.id) и timestamp уже успешно отправленных в Garmin взвешиваний. Повторная отправка одного и того же взвешивания блокируется.

### **NFR-2: Обработка ошибок сети (Транзакционность токена)**

* **Критическое правило:** Новый nextChangesToken сохраняется в локальное хранилище **только после того**, как модуль отправки в Garmin вернул успешный статус (Result.Success).  
* Если API Garmin недоступен (ошибка сети, 5xx), токен в DataStore **не обновляется**, а воркер возвращает ListenableWorker.Result.retry(). При следующем запуске данные будут вычитаны заново по старому токену.

### **NFR-3: Задержка записи сопутствующих метрик (Race Condition)**

* *Сценарий:* Синхронизация запустилась ровно в ту секунду, когда приложение весов записало WeightRecord, но еще не успело записать BodyFatRecord.  
* *Решение:* Если найдена запись WeightRecord, возраст которой (Instant.now() \- record.time) меньше 30 секунд, и у нее нет сопутствующих метрик жира/мышц — отложить обработку этого измерения до следующего цикла (или сделать delay(5000) и перепроверить окно через readRecords).

## **6\. Архитектура и Контракт интеграции**

Модуль реализуется как изолированный слой данных и взаимодействует с существующим кодом через чистый интерфейс:

Kotlin  
// Сущность, передаваемая в существующий модуль Garmin  
data class BodyCompositionPayload(  
    val recordId: String,  
    val timestamp: Instant,  
    val weightKg: Double,  
    val bodyFatPercentage: Double? \= null,  
    val boneMassKg: Double? \= null,  
    val leanBodyMassKg: Double? \= null,  
    val bodyWaterPercentage: Double? \= null,  
    val basalMetabolicRateKcal: Double? \= null,  
    val sourceAppPackage: String  
)

// Интерфейс существующего модуля отправки (Реализован вне рамок этого PRD)  
interface GarminSyncGateway {  
    suspend fun uploadBodyComposition(payload: BodyCompositionPayload): Result\<Unit\>  
}

## **7\. Критерии приемки (Acceptance Criteria)**

> 1. **AC-1 (Полный цикл):** Пользователь взвешивается на весах Tefal $\rightarrow$ данные появляются в Health Connect $\rightarrow$ при открытии приложения (или по расписанию воркера) вес и процент жира склеиваются в один BodyCompositionPayload и передаются в GarminSyncGateway.  
> 2. **AC-2 (Отказоустойчивость):** При отключенном интернете во время работы воркера данные из Health Connect читаются, отправка в Garmin падает с ошибкой, ChangesToken не перезаписывается. При появлении сети данные успешно досылаются.  
> 3. **AC-3 (Отсутствие дублей):** Принудительное нажатие кнопки «Синхронизировать» 5 раз подряд не приводит к повторным вызовам GarminSyncGateway для уже отправленного веса.  
> 4. **AC-4 (Деградация прав):** Если пользователь в настройках Android отзывает право на фоновое чтение, приложение не падает с SecurityException в фоне, а корректно переходит в режим синхронизации только при открытом UI.
